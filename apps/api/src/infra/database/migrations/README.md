# Migrations

Generated by `pnpm --filter api db:generate` (`drizzle-kit@0.31.10`), applied by
`pnpm --filter api db:migrate` (`drizzle-orm`'s own migrator). Forward-only:
once a file here has been applied anywhere shared it is never edited, because
the runtime migrator hashes the file body — an edit makes an applied migration
look new and it runs again.

A generated migration is a **draft**. Read it before committing: Drizzle emits
`DROP COLUMN` + `ADD COLUMN` where a rename was meant, and it will not generate
either the `srid` on a `geometry` column or the `gist((position::geography))`
index at all ([ADR-0018](../../../../../../docs/decisions/ADR-0018-spatial-index-on-the-geography-cast.md)).
Those are written by hand.

## Why `0000_enable_postgis` has no snapshot (issue #49)

`meta/` holds one `<idx>_snapshot.json` per migration **except the first**, and
that asymmetry is deliberate rather than an oversight to be tidied up later.

`0000_enable_postgis.sql` was written by hand in EPIC 1 (issue #22): it is
`CREATE EXTENSION IF NOT EXISTS postgis;`, there were no tables yet, and
`drizzle-kit generate` had nothing to diff and would not have produced it.
Everything from `0001` on is generated and brought its own snapshot.

The open question was whether the generator would later mis-diff because of the
gap. It does not, and this was settled against the artifact, not the docs
(CLAUDE.md §9) — by reading `drizzle-kit@0.31.10`'s own bundle and by a real
run:

- `prepareOutFolder` reads `meta/_journal.json` and then treats **every file in
  `meta/` not starting with `_`** as a snapshot. It never looks for one per
  journal entry, so a journal entry without a snapshot is not a state it can
  notice.
- `validateWithReport` keys the snapshots it found by their `prevId`. The diff
  is taken against the last snapshot in sorted order — here `0006` — not
  against a walk of the journal.
- Verified end to end: with a throwaway table added to the schema barrel,
  `db:generate` emitted `0007_probe_table.sql` containing exactly
  `CREATE TABLE "probe_table" (…)` and nothing else. No warning, no recreate of
  anything the journal already accounts for. The probe was then reverted.

**Do not add a `0000_snapshot.json`.** It is not merely unnecessary — it breaks
generation. A snapshot for `0000` would have to claim the chain root
(`prevId: "00000000-0000-0000-0000-000000000000"`), which `0001_snapshot.json`
already claims, and two snapshots sharing a parent is what `validateWithReport`
reports as a collision. `prepareMigrationFolder` answers a collision with
`process.exit(0)`: `db:generate` would print a line, exit **successfully**, and
write nothing, for everyone, until someone deleted the file again.

`test/database.migration-meta.test.ts` asserts all of this — the chain has one
root and no collision, the journal runs exactly one entry ahead of the
snapshots, and `0000_enable_postgis.sql`'s hash has not moved.
